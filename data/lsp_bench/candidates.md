### Recall audits and pattern revision

Two audits each read a seeded random sample of 40 non-retrieved issues per server (`scripts/lsp_bench/recall_audit.py`). Audit 1 ran against the first pattern set; its misses were all edit-validity (R4) reports whose wording the first set lacked, so the patterns were revised (round 2, below) and the newly retrieved issues were screened like the rest. Audit 2 ran against the revised patterns. Misses that no pattern retrieves are added to the retrieved set with pattern id `audit` (tsserver #44374, #57498, rust-analyzer #14841, gopls #35548).

  - gopls #36824: R4: import organization on a single-line file drops the function

- Audit seed 20260924 (round 2 patterns): 3 of 160 sampled non-retrieved issues would have been kept (pyright 0/40, tsserver 1/40, rust-analyzer 1/40, gopls 1/40).

### Screening

Every retrieved issue was read (title, labels, cleaned body excerpt, fix subject; for gopls also the fix commit message; full bodies and commit messages when the excerpt was not enough) and decided once: kept with a primary class, a grade, one factual sentence and a trigger hint, or rejected with one reason code. Decisions are in `scripts/lsp_bench/decisions/*.py`; the build step fails unless every retrieved issue is decided exactly once. Trigger subtypes: R1 edit-undo, typing, open-close, file-op, config, dependency-edit, query-order, race; R2 resolve, semtok-delta, stale-edit; R3 pull-push, semtok-range, highlight-refs, def-consistency, other-route; R4 quickfix, codeaction-other, format, completion, organize; R5 blank-lines, comment, whitespace, crlf, non-ascii, file-edge.

### Version mapping

`mapping_confidence`: high = the release window comes from git ancestry of the located fix commit (or, for pyright without a commit, the maintainer's release comment) and the cross-checks agree (compare API for tsserver and gopls, npm publish date after the merge); medium = window from the pyright label event, a cross-check disagrees, a fix spans releases, or no earlier release exists; low = close-date heuristic or the fix is in no release yet; none = no fix commit or PR could be located.

- **pyright**: fix commits = squash commit of a merged closing PR, `closer_commit`, backfilled commits (merges excluded). post = lowest `1.0.x`/`1.1.x` tag containing every fix commit (`git tag --contains`), pre = highest release below it containing none. Without a fix commit: the maintainer's comment naming the release (issue comments API, high), else the first npm release after the `addressed in next version` label event (issue events API, medium), else the latest release before the issue closed (low). Versions checked against `npm view pyright time --json`; the npm package ships `pyright-langserver` only from 1.1.52, so windows starting earlier are marked not obtainable from npm (the same-version VS Code extension or a build of the git tag would be needed). A 1.1.80 language server was started on the local Node 24 as a smoke test.
- **tsserver**: squash commit of the merged closing PR on main plus release-branch picks (`Pick PR #N`, `Cherry-pick PR #N`) in a treeless clone; post = lowest stable `vX.Y.Z` tag (X < 7) containing one of them, pre = highest stable release below post containing none; both nearest tags confirmed with the GitHub compare API (base=tag, head=squash commit; `behind`/`identical` = contained; a pick makes the post tag `diverged`). Merge date checked against `npm view typescript time --json`. A tighter nightly window (`X.Y.Z-dev.YYYYMMDD` whose published `gitHead` does / does not contain the fix) is recorded in `mapping_extra`. tsserver is not an LSP server; `build_notes` names the typescript-language-server release contemporary with the post-fix build as the wrapper (pairing untested).
- **rust-analyzer**: merge commit of the closing PR (`Merge pull request #N`, bors `Merge #N`, homu `Auto merge of #N`) in a treeless clone, else `closer_commit`; post = earliest weekly date tag containing it, pre = latest date tag before post not containing it; the date rule (last release on or before the merge day, first after it) is recorded and differs in the rows flagged `date_rule_differs`. Builds: the release must carry `rust-analyzer-aarch64-apple-darwin.gz` (GitHub releases API); that asset exists from 2020-12-28 on, and when the exact pre or post release lacks it (e.g. 2024-09-23) the window is widened to the nearest release that has it (`mapping_extra`).
- **gopls**: fix = `closer_commit` (golang/tools), else the backfilled commit saying `Fixes golang/go#N`; cherry-picks found by `[gopls-release-branch.0.X]` subject. A release contains the fix when the fix (or a pick) is an ancestor of its `gopls/vX.Y.Z` tag and, for fixes outside `gopls/`, of the x/tools commit pinned in that release's `go.mod` (proxy.golang.org); v0.1.x have no tag and use the pinned commit. The two nearest tags are confirmed with the compare API. Builds: module versions on proxy.golang.org (`go install golang.org/x/tools/gopls@vX.Y.Z`); `build_notes` gives each release's `go` directive and the newest Go release at its date. Every pre/post version was compiled (`gopls_builds.py`): first with the local Go, using a wrapper module for v0.1.0-v0.5.3 and v0.6.8 (their go.mod has `replace golang.org/x/tools => ../`, which `go install` refuses since Go 1.16), then with downloaded toolchains (`GOTOOLCHAIN` = the release's go.mod version, the .0 release of its Go era, go1.21.0; never below the go.mod version); the toolchain that worked is in `build_notes`. Of 73 gopls versions checked, 55 built with the local toolchain, 18 only with an older downloaded toolchain, and 0 did not build.

### Ranking

score = grade (A +30, B +18, C +6) + 20 if both builds are obtainable + mapping confidence (high +8, medium +4, low +0, none -10) + 5 if the fix changed tests; the issue body itself is not scored (pilot bodies are truncated at 2,000 characters, which removes the reproduction from most gopls reports), the screening grade carries reproduction quality; penalties race -6, codeaction-other -4, other-route -4, -3 if the needed transformation is outside T1-T3, -4 for telemetry-only reports, -2 per set-up marker for environment set-up in the trigger hint or note (needs/requires, cargo check/flycheck, third-party, install, proc macro, build script, vendor, module cache, large project, checkout; at most -4; configuration and file operations are not penalised because they are ordinary R1 history steps). Many candidates tie at the top score, so the tie-break matters: within a score, servers are interleaved and, within a server, oracle classes are interleaved (rarer class first, each ordered by more recent fix). Top 80: the best 15 per server among candidates with both builds and a bug present in a released pre-fix build, then the best remaining scores; `scriptability_rank` orders the top 80 first, then the rest.

### Uncertainties

- Screening is a single reading per slice; borderline keeps are graded C and described in `notes`. Several R4 keeps need the edit-validity check to count type errors (unresolved imports) rather than syntax errors only, and the 17 `codeaction-other` keeps are not diagnostic-attached quick fixes, so R4(a) as designed would not apply them.
- 18 keeps (mostly R5) need a transformation outside T1-T3 (LF to CRLF, same-line non-ASCII text, trailing newline at EOF, same-line trailing comment); their hints say so. 4 R3 keeps use a route pair outside the four designed checks (`other-route`).
- pyright: most `addressed in next version` issues have no commit that names them; those windows rest on the maintainer's release comment or on the label event (medium confidence). The label is sometimes added before the fix is committed, so `post` can be one release early when the fix lands after the next release is cut.
- Regressions introduced and fixed between two consecutive releases have no released pre-fix build with the bug (`no_released_bug`); a build of the fix's parent commit would be needed.
- gopls releases before v0.2.0 have no tag in golang/tools; issues fixed before v0.1.0 have no released pre-fix build. The build check compiles each release but does not run it: old gopls drives the `go` command found on PATH, so a benchmark run should put a Go of the release's era on PATH (see `build_notes`).
- tsserver fixes merged after the 6.0 branch cut that only ship in 7.x (native) are out of scope and have no build.
- Network use: 681 responses from api.github.com, 181 responses from proxy.golang.org, 140 responses from registry.npmjs.org (each fetched once and cached under `temp/lsp_bench/cache/http`); this run made 0 uncached GitHub calls and 0 other uncached calls.
